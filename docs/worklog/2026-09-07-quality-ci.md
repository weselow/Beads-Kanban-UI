# 2026-09-07 — проверки в CI (beads-web-zct)

До этого ни один рабочий процесс не запускал проверки: `release.yml` срабатывает
только на тег, `ci.yml` только обновляет хеш Nix. Регрессия могла попасть в main
и уехать в выпуск незамеченной. Добавлен `.github/workflows/quality.yml` — на
pull request в main, на push в main и вручную.

**Почему именно так.**

- Задание для сервера создаёт **пустую** папку `out/`. `server/src/main.rs`
  встраивает `../out/` через rust-embed, и папка обязана существовать на этапе
  сборки. Проверил: пустой достаточно, полная сборка интерфейса ради тестов не
  нужна и экономит минуты.
- `cargo test --lib --bins`, а не голый `cargo test`. `tests/memory_bd.rs`
  вызывает `bd`, который поднимает сервер Dolt и может подвиснуть. При этом
  `clippy --all-targets` компилирует все цели, так что поломка интеграционной
  проверки всё равно заметна — её просто не запускают.
- `next lint --max-warnings 0` — так же строго, как в хуке перед коммитом, иначе
  предупреждение, заблокированное локально, проходило бы в CI.

**Что проверить, если сломается.** Задание для сервера падает на этапе сборки со
словами про несуществующую папку — значит, изменили путь в атрибуте `#[folder]`
в `main.rs`, и шаг `mkdir -p out` больше не совпадает с ним. Задание для
интерфейса падает на `npm ci` — рассинхрон `package-lock.json` и `package.json`.

**Что намеренно не трогали.** `ci.yml` и `release.yml` — они делают своё и
оставлены как есть. Проверки не гоняются на macOS и Windows, только на Linux:
кросс-платформенную сборку и так делает `release.yml`.
